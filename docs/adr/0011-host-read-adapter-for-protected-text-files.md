# 宿主读取适配器：受控环境下的文本读取由外部白名单程序代理

部分用户机器部署亿赛通等终端透明加密：宿主进程不在白名单内，读取 txt/json/xml 只能拿到密文，标签文件与项目配置都不可读，而宿主写出的文件按策略一律以密文落盘。插件层无法承担这件事——代码型插件运行在 AppContainer 中，只获得插件包与声明使用的解释器目录，manifest 权限面不开放 `spawn`（ADR 0005），无法启动白名单程序；AGENTS.md §10 又禁止项目打开、数据保存等关键路径同步等待插件。因此由宿主新增「读取适配器」作为所有文本读取的唯一入口，内置原生、Python、命令三种预设；接口必须批量（一次调用读取多个路径），因为一次 YOLO/VOC 导入会读取数百上千个小文件；配置属机器级，项目文件与插件清单都不得携带任何命令模板（否则打开他人项目等于执行任意命令）；适配器不可用或读取自检失败时明确阻断并报错，禁止静默回退原生读取——乱码会被成功读入，静默污染标注数据。写入侧保持原生：驱动对任何进程的写入都加密，宿主写出的文件在受控机器上本来就是密文；相应地该模式下「写入后回读校验」不成立，保存成败以写入调用的返回为准。读取模式按适配器注册：新增一种模式只需新增一个适配器实现与其配置元数据，不新增读取路径、不改动调用方。

**Status**: accepted

**Considered Options**
- 新增插件扩展类型（宿主代执行白名单程序，插件负责编排与解析）：保留「用户自己写插件」的形态，但要新增扩展类型与受控外部工具执行权限、修订 ADR 0005 的信任基线，并为关键路径同步等待开例外条款；可编程性的收益由安全面与契约面同时扩大来交换
- 插件运行在白名单解释器内（宿主用白名单 python 执行插件脚本，插件直接读写明文）：最贴近「插件 Hook 文件读写」的原意，但插件脱离 AppContainer 并以用户身份获得任意文件访问，等于给插件开一条任意代码执行通道
- 只做读侧、由用户手工预处理：每次导入导出都要人工解密，不可接受
- 读 + 写双向代理：写侧没有需求——写入加密与进程是否白名单无关，双向代理只会让「导出结果仍受管控」这一策略预期落空

**Consequences**
- 宿主所有文本读路径统一走适配器：标签文件、项目配置与导入来源文件、应用数据目录下的标签/模板/快捷键/模型库/资源限制配置；插件经宿主 `fs.read` 代理的读取自动获得明文
- 读取适配器是文本读取的唯一 seam：模式注册表集中声明名称、所需配置字段与自检方式，界面与配置校验由注册表驱动；新增模式不得引入第二条读取路径
- 无插件契约变更：manifest schema、宿主 API、能力与协议版本面均保持 v1，不需要 bump（§10 边界影响评估结论）
- 读取自检（宿主写出含多字节字符的临时文本、再经适配器读回比对）成为配置校验与会话首次读取的健康检查；自检失败必须显式可见，不能靠「读到乱码」发现
- 命令模式的编码风险（`cmd` 的 `type` 走控制台代码页，可能转码破坏 UTF-8 内容）与批量性能（不得按文件数重复启动外部程序）成为适配器接口的硬要求，而非优化项
- 依赖外部白名单程序可用，而厂商文档把「通用解释器加白」列为不建议的配置：策略一旦收紧，必须能被自检立即发现并给出可定位的失败原因
