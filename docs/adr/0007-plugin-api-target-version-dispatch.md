# 宿主 API 版本模型：目标版本分派 + 能力级版本

插件 API 的破坏性升级采用「开新版本号 + 宿主多版本实现并存」模型：同一版本号内宿主承诺增量兼容（新增可选字段、不删不改语义），破坏性变更必须发布新版本号，宿主保留旧版本实现并按插件声明的目标版本（`apiVersion.min`）分派。版本粒度分两层——整体版本覆盖 `hello`/`fs`/`config.migrate` 等基础能力，业务能力（`exporter`、`prelabel`）各自独立版本，因此部分能力的破坏性升级只影响声明使用该能力的插件。旧版本实现按弃用策略（兼容期 ≥2 个 host API 版本）保留后移除，期满后声明旧版本的插件在协商阶段以新增标准错误码 `API_VERSION_UNSUPPORTED` 明确失败，而不是静默按新语义运行。不使用 `max` 字段：无上界语义在破坏性升级下悬空（宿主无法从 `min` 推断插件对新版本的接受度），区间声明又与分派语义重复；插件只需声明它写的是哪个版本。

**Status**: accepted

**Considered Options**
- 维持 `min` + `max?`（无上界）：日常增量升级无问题，但破坏性升级（尤其部分能力破坏）时旧插件会静默跑错，不可诊断
- `min` + `max` 区间 + 多版本实现：`max` 与「宿主按目标版本分派」语义重复，徒增插件作者声明负担
- 每协议方法独立版本：粒度最细但协商表膨胀、宿主多版本维护成本不可控，v1 无此必要

**Consequences**
- 宿主侧对业务能力维护多版本实现，维护成本随破坏性升级次数增长；「向后兼容优先」约束与弃用期（≥2 个 host API 版本）限制同时存活的版本数
- 协议错误码从 9 个增至 10 个（`API_VERSION_UNSUPPORTED`），纯增量，既有插件不受影响；conformance 测试与文档同步
- 协商时机：安装时 + 每次启动握手；握手响应含宿主支持的能力版本表
