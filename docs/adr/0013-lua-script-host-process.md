# Lua 脚本经独立宿主进程执行，不进插件体系、不叠加平台沙箱

应用内数据处理（脚本）以独立宿主进程承载 Lua 解释器：宿主是应用自带的二进制，与主程序只交换「请求 / 响应 / 进度 / 取消」的最小 NDJSON 协议，复用 `process_control` 的进程组、Job Object 与 `terminate_process_tree` 原语；不进入插件注册表、授权流程、安全模式与版本面。原因：脚本的事实源（图片集与标注）在前端 store，脚本本身是「数据进、数据出」的变换，没有任何需要授权的资源；把每次现写的临时脚本塞进安装/授权路径语义不对，而且 ADR 0012 规定代码型插件仅 Windows 宿主可用，会让脚本在 Linux 服务端形态下连带被禁。信任边界取「只防手滑」：不自动发现、不自动执行任何来自项目目录或其他来源的脚本，项目配置永不携带脚本内容；隔离由 Lua 安全子集标准库、仅接受文本 chunk、进程终止、内存与时间上限构成，不叠加 AppContainer 等平台级沙箱，两形态行为保持一致。若产品将来开放脚本分发、项目自带脚本自动运行或服务端任意用户提交脚本，必须先升级隔离等级再开放对应入口。

**Status**: accepted

**Considered Options**
- 前端 WASM Lua（Worker）：隔离与取消由 worker 免费提供，且两形态零桥接改动；但数据要离开 store 经 IPC 往返，跨图逻辑与内存受 worker 限额约束，缺少 Lua 模块生态，引擎只存在于界面进程
- Rust 进程内 mlua：最快，取消可到指令级；但用户脚本与未保存标注同进程，一次死循环或内存耗尽赔上用户全部内存标注，解释器漏洞面直接落在宿主进程
- 复用插件运行时（脚本当内置插件）：白送握手、超时、权限、故障计数；但需新增业务能力版本与 Schema/conformance 全套，且非 Windows 宿主不可用

**Consequences**
- 脚本宿主成为新的随包二进制，打包与两种形态的交付都要覆盖；任一形态不可用时必须在界面如实说明，不得静默降级
- 进程 framing、超时与进程组终止与插件运行时同构但不同源，可抽公共模块收敛
- 安全模式与自动禁用不适用于脚本：不存在「已安装的插件」这一状态
- 不新增宿主 API 业务能力版本，不改插件 manifest 与协议 Schema（`AGENTS.md` §10 的影响评估结论：对插件契约无影响）
