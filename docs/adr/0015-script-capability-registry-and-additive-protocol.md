# 脚本能力面按注册表声明、数据按段落扩展、协议按版本增量演进

主程序与脚本宿主之间的能力面以「命令注册表」集中声明：命令名、参数、返回、错误语义与所需数据段落登记在一处，新增能力只改注册表加一个实现，不引入第二条数据通路（与读取适配器的模式注册表同一种做法）；命令面带 API 版本常量，脚本可据此判断兼容。数据面按段落传输（图片与标注为首个段落），新增宿主数据即新增段落，协议只做增量字段扩展：带版本字段与启动协商，容忍未知字段，未知命令返回可识别的错误。能力扩展分三档并明示代价——①只依赖快照的能力：加一个命令实现即完成；②需要宿主新数据的能力：增加一个快照段落；③需要宿主动作或惰性拉取的能力（读写文件、保存、导出、调用预打标）：必须新增「宿主 → runner 请求」方向，属大改，须先开 ADR，v1 不做。原因：脚本的价值在于能力持续增长，若每次扩展都要新增消息类型与权限语义，扩展成本会压死这个功能；而 v1 又不应为未验证的惰性需求预先背上三跳反向 RPC（见 ADR 0014 的取舍）。

**Status**: accepted

**Considered Options**
- 每个能力直接挂全局函数、数据写死在单个请求结构里：改动最小，但新增一类数据就要改协议结构，能力一多即失控
- 一开始就做完整反向 RPC 与细粒度能力协商：一步到位，但要为未验证的需求先付协议方向、超时与权限语义的成本
- 让脚本宿主直接读文件（项目文件与脚本库）：手脚最省，但一次性破坏受控环境适配（ADR 0011）与「宿主零文件能力」的隔离基线

**Consequences**
- 脚本库（应用数据目录下的 `.lua`）是新的宿主文本读路径：必须接入读取适配器（ADR 0011）并复用既有文本读写命令，不得新增第二条读取路径；写入侧保持原生，受控环境下保存成败以写入调用返回为准
- 资源上限（宿主进程内存——覆盖整份快照与结果缓冲、总超时）比照 `prelabel-resource-limits` 的既有模式：机器级配置、校验与执行共用、默认值集中在 `src/lib/defaults/`；数值默认值待原型实测后确定；单图超时不在 v1——一次运行执行一遍，无可靠单图计时边界，待定义逐图执行入口时再议
- 脚本运行作为一项「操作」登记进操作注册表并占用「项目标注」资源；用户可见文案进 `src/i18n/`，宿主侧错误文案进 `src-tauri/src/i18n/zh_cn.rs`
- 插件契约面不变：不改 manifest schema、协议与宿主 API 版本（`AGENTS.md` §10 影响评估结论）
