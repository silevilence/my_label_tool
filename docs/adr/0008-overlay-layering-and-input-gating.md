# 遮罩分层与输入门禁单一裁决

前端遮罩（弹窗、菜单、浮层）统一由一个 Overlay 模块渲染：组件挂载即自注册进栈，栈对外只暴露「是否存在阻塞级遮罩 / 是否存在轻量级遮罩 / 深度」；所有键盘消费者通过同一谓词决定是否响应，而不是各自维护「哪些弹窗开着」的名单。分两层的理由是这两类界面今天同时存在且行为预期不同：模态弹窗应独占全部快捷键与焦点，右键菜单、搜索浮层只应吞掉画布写操作类动作而不阻断保存、缩放等全局动作。

**Status**: accepted

**Considered Options**
- 一类「遮罩即全阻」：最好解释，但设置面板打开时 `Ctrl+S` 也失效，且与菜单的实际交互预期不符
- 一类「只把模态弹窗的手写名单换成栈非空」：改动最小，但保留「菜单开着时画布被快捷键误改」这一现有行为
- 按键级所有权（每个动作声明可在哪些层生效）：最精确，但把复杂度平摊到每个动作表项，现有场景不需要

**Consequences**
- 快捷键动作表因此需要 `scope: canvas | global` 字段，`light` 遮罩只吞 `canvas` 类动作
- `z-index` 改由栈深度推导，取代现状散落在 13 个文件的 50/60/65/85/90/95/100 七个值
- 新遮罩必须经 Overlay 渲染；直接书写 `fixed inset-0` 视为破坏门禁（登记遗漏不再可能发生）
- 迁移范围为前端既有 17 个遮罩；Rust 侧与插件协议不受影响
