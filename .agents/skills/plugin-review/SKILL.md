# Plugin Review (my_label_tool)

项目级插件相关代码审查技能。所有插件相关开发成果的审查都必须遵守本技能流程。

## 1. 审查前必读（必须）

- `AGENTS.md` — §10 插件系统开发约束（本次审查的主依据）+ 常规编码规范
- `CONTEXT.md` — 插件系统术语表；审查输出使用其中词汇
- `docs/adr/0003-plugin-runtime-external-process-stdio.md`、`0004-exporter-plugins-use-code-plugin-protocol.md`、`0005-plugin-trust-no-signing-minimal-permissions.md`、`0006-plugin-config-opaque-json-with-migration-calls.md`
- `ROADMAP.md` 插件系统章节 — 对应任务的验收项
- 被审查代码触及的核心契约：`src/types/annotation.ts`、`src/types/export.ts`、`src/types/prelabel.ts`、`src/lib/importers.ts`（ProjectConfig）、`src/lib/tauri-api.ts`

## 2. 审查规则（必须）

- **默认约束已是最新**：审查时不得修改任何规范文档（AGENTS.md、CONTEXT.md、docs/adr/、ROADMAP.md），也不得修改被审查代码——审查只报告，修复由编码流程执行。
- **双向检查**：既查插件代码是否违反约束，也查核心改动是否破坏插件层契约（边界影响评估：标注数据模型、ProjectConfig、导出结构、预打标契约、Tauri commands 的改动是否同步更新了 Schema/兼容性说明/conformance 测试）。
- 按以下维度逐条过检，代码与约束对不上 → 报问题：违反条款（文件+章节）+ 证据（`文件:行号`）+ 严重度。
  - **契约与 Schema**：类型先行且带版本号、前后端字段一一对应、JSON Schema 与校验测试存在
  - **ID 与版本分层**：反向域名命名空间、ID 不复用、三层版本独立、业务能力独立版本、manifest 以 `apiVersion.min` 声明目标版本且宿主按版本分派（无 max 字段）、破坏性变更走开新版本号 + 弃用期保留流程、协议消息带协议版本、版本号独立于主程序版本（禁止随主程序发版无脑同步 bump）
  - **能力声明**：以握手能力声明为准而非版本号推断；新增能力走 manifest + 协商
  - **向后兼容**：新增字段可选有默认值；无删除字段/改变语义/重排必需字段；弃用流程（deprecated → 替代 → 兼容期 → 移除）
  - **权限与隔离**：宿主协议代理、权限模型未被绕过、无直接暴露 Tauri commands/文件句柄；Windows 代码型插件使用 AppContainer 且失败关闭，只临时授权包与声明使用的系统解释器运行目录，宿主环境按白名单重建，直接包外文件、宿主秘密环境变量和 socket 被 OS 级测试拒绝，并真实启动包内 EXE/系统 Python（环境变量离线标志不算隔离证据）；启动失败与进程结束不遗留 ACL/profile；调用有超时；关键路径不同步等待插件；连续失败 3 次自动禁用；安全模式禁代码型插件
  - **目录与工程约定**：目录归属正确、tauri-api 封装、组件内无直接 invoke、文案进 i18n、无 `any`、术语符合 CONTEXT.md
  - **测试**：manifest 校验/协议解析/权限判定/配置迁移/故障隔离有单测；新增错误码/消息类型/协议行为同步 conformance 测试
- 严重度分级固定为项目用语：阻断（违反 MUST 且影响正确性/安全/数据）、严重（违反 MUST）、一般（违反 SHOULD 或局部偏差）、建议（可改进项）。禁止混用其他分级体系（如 Critical/High/Medium/Low）。
- **证据核实**：报告中的每一条 `文件:行号` 必须重读源文件逐条核实——行号指向的行确实包含所述问题；凭记忆或估算引用的行号视为证据无效，发现后必须修正再报。
- **维度全覆盖**：七个维度逐条过检，每个维度必须给出明确结论（发现问题或注明"通过"），不得留空维度；引用 ADR 时标注编号（如 ADR 0006），引用约束时标注 AGENTS.md §10 条款。
- 阻断级问题存在 → 结论"不通过"，不得交付。

## 3. 规范缺陷处理（必须）

若审查中发现约束文档本身有错误、缺失或自相矛盾：

- **不得自行修改约束文档**，也不得按"推测的意图"审查。
- 作为独立问题报告：文档文件 + 条款 + 缺陷描述 + 建议修改方向。
- 报告交由用户决定是否走 `plugin-coding` 的逐点确认流程修改约束；约束修改完成前，按现有条款判定代码合规性。

## 4. 输出格式（必须）

```
## 审查结果
- 范围：<功能 / 提交 / 文件>
- 结论：通过 / 不通过（阻断 N / 严重 N / 一般 N / 建议 N）

| 维度 | 条目 | 结果 | 证据 | 严重度 |
|---|---|---|---|---|
| 权限与隔离 | 宿主代理 | 不通过 | src-tauri/src/plugins/runtime.rs:42 | 严重 |
```

每条证据行号必须经过源文件复核（见 §2 证据核实）。另附"规范缺陷"清单（如有）：文档文件 + 条款 + 缺陷 + 建议；以及"约束引用"清单：每条已通过的关键维度对应的约束出处（AGENTS.md §10 条款 / ADR 编号），便于编码方核对。

## 5. 禁止事项

- 禁止在审查中修改代码或规范文档——审查只报告，修复由编码流程执行。
- 禁止跳过任一审查维度。
- 禁止以"用户口头要求"覆盖约束条款；口头要求与约束冲突时，报告冲突并按 §3 处理。
